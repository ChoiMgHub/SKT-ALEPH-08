# 인증 구현 설명 · 여섯 항목

## ① 무엇으로 붙였나

**라이브러리를 이용한 직접 구현**이다. WebAuthn 등록·인증 옵션 생성과 공개키 검증은 `@simplewebauthn/server 14.0.3`, 기기의 WebAuthn 호출과 JSON 변환은 `@simplewebauthn/browser 14.0.0`을 사용한다. 인증 SaaS·소셜 로그인·사이트 비밀번호는 사용하지 않는다. 서버는 Cloudflare Workers, DB는 D1이다. 라이브러리가 검증한 결과를 확인한 뒤 우리 코드가 계정·세션·소유권을 처리한다.

개인키는 기기 또는 선택한 패스키 제공자가 관리하며 이 앱 서버에 보내지 않는다. 동기화형 패스키는 제공자의 정책에 따라 암호화·동기화될 수 있다. 서버가 받는 공개키는 서명을 검증하는 값이며 비밀번호가 아니다. 지문·PIN·패턴은 기기에서 키 사용을 승인하는 수단으로, 이 앱의 입력 항목이 아니다.

공식 자료: [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server), [browser](https://simplewebauthn.dev/docs/packages/browser), [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/), [Google 패스키 지원 환경](https://developers.google.com/identity/passkeys/supported-environments).

## ② 왜 이걸 골랐나

서명 검증·COSE 공개키 해석·인증기 응답 검사를 직접 암호 알고리즘으로 다시 구현하지 않기 위해 유지보수되는 라이브러리를 선택했다. T07의 비밀번호 해시 대신 공개키 인증 흐름을 배우되, 로그인 후 세션과 계정 소유권 검사는 계속 필요하다. 공개 소개는 인증 없이 열려야 하므로 웹사이트 전체에 외부 로그인 장벽을 두지 않는다.

학원 PC의 Windows 계정 설정을 바꾸지 않고 본인 갤럭시 Chrome에서 HTTPS 주소를 직접 여는 방향으로 정했다. 갤럭시의 지문·PIN·패턴 사용과 Chrome 사용 가능 여부는 사용자가 확인했다. 사용자는 운영 배포 후 갤럭시 Chrome에서 첫 키 등록, 메모 3개 확인, 로그아웃 후 지문 승인 재로그인에 성공했다. 기본 서비스를 Google로 바꾼 뒤 같은 계정에 두 번째 키가 등록된 목록과 성공 안내도 제공했다. 사용자가 서버의 실제 인증 키 표시로 예비 키 인증과 기본 키 삭제 뒤 남은 키 인증을 확인했다. B 계정 등록·로그인 후 일반 로그인에서 A로 돌아올 때 실패해 해당 경로를 보완 중이다.

## ③ 어디를 어떻게 고쳤나

T01 `89fabfcff6c9a2a07dc4350fa0858f35060bdefb`의 공개 소개 본문과 활동·근거 링크를 이어받아 아래에 패스키 영역을 추가했다. 공개 연락 이메일은 가상 주소로 교체했다. 기존 공개 이름·학습 배경은 유지했다. 비공개 메모 3개는 서버가 가상 내용으로 만들며 공개 HTML·브라우저 JS에 원문을 넣지 않는다.

| 흐름 | 브라우저 위치 | 서버 위치·저장 |
|---|---|---|
| 새 등록 | `src/client.js`의 `registration()` → `startRegistration()` | `src/worker.js`의 `/api/auth/registration/options`, `/verify` → `generateRegistrationOptions`, `verifyRegistrationResponse` |
| 키 추가 | 같은 함수의 `mode: add` | 로그인 소유자만 허용, 5분 이내 인증 필요, 기존 키 제외 목록 제공 |
| 로그인 | 로그인 버튼 → `startAuthentication()` | `/api/auth/login/options`, `/verify` → `generateAuthenticationOptions`, `verifyAuthenticationResponse` |
| 로그아웃 | 로그아웃 버튼 | `/api/auth/logout` → 세션 해시와 해당 브라우저 미완료 질문 삭제 |
| 비공개 조회 | `refresh()` | `session()` 확인 후 `/api/private`, `/api/private/:id`의 `WHERE user_id=?` |
| 키 삭제 | 키 목록의 삭제 버튼 | `/api/credentials/:id`의 소유권·최근 인증·최소 한 키 검사 |

서버가 매번 만든 무작위 challenge는 `challenges` 테이블에 5분간 보관한다. HttpOnly 흐름 쿠키의 SHA-256 해시에 묶는다. 검증 시 `DELETE ... RETURNING`으로 한 번만 꺼내며 **실패한 검증에서도 소모**한다. 사용·만료 질문의 재전송은 401이다. 등록 취소는 질문만 폐기하고 사용자·키를 생성하지 않는다.

검증에는 고정 `ORIGIN`, `RP_ID`, 서버 질문, 사용자 확인(UV) 조건을 사용한다. 인증 성공 시 저장 공개키로 서명을 확인하고 카운터를 조건부 갱신한다. 세션은 32바이트 무작위 토큰이며 DB에는 해시만 저장한다. 운영 쿠키는 `__Host-` 접두사·Secure·HttpOnly·SameSite=Strict·Path=/, 유효시간은 1시간이다. 만료 정각부터 거부한다. 쿠키·토큰을 확인 파일에 적지 않는다.

메모·키 목록은 세션의 소유자로 필터한다. URL·헤더·본문의 `user_id`는 소유권 결정에 쓰지 않는다. 남의 원문 ID 조회·수정·삭제는 403, 익명 API는 401이다. 비로그인 `/private` 화면은 공개 소개의 로그인 영역으로 이동한다. 로그아웃·탭 숨김·다른 계정 전환에서 기존 비공개 DOM을 지운다. 모든 응답은 no-store다.

키 이름·등록 날짜·공개키를 본인에게 보여준다. 저장소 이름은 **사용자 자기 기입 정보**이며 인증기가 보장한 값이 아니다. 목록에서 실제 키 수를 확인해야 한다. 마지막 키 삭제는 원자적 SQL로 차단한다. 지운 키로 만든 기존 세션은 외래키 CASCADE로 함께 회수한다. 모든 기기·키를 분실한 경우 별도 복구 기능은 없으며, 가상 아이디만으로 키를 재등록하거나 원문을 타인에게 넘기지 않는다.

## ④ 안 열리는 걸 확인한 기록

[`public/verification.json`](../public/verification.json)과 [`public/verification.html`](../public/verification.html)은 **격리 workerd/D1에서 실행한 기록**이다. 가상 A/B 계정과 소프트웨어 인증기가 P-256 키를 만들고 실제 서명을 생성했다. 배포할 동일 번들의 검증 코드가 허용·거부를 결정했다. 검증기를 성공으로 고정하는 mock은 사용하지 않았다. Cookie·Set-Cookie는 가렸다. 개인키는 기록·저장소·공개 파일로 내보내지 않았다.

네 가지 확인과 추가 확인:

1. 로그인한 A의 API 조회 200 / 익명 동일 조회 401.
2. B 본인의 원문 조회 200 / A가 B 원문을 조회·수정·삭제하면 403. 반대 방향도 확인하고 피해자 건수·본문이 그대로인지 비교.
3. 새 질문과 올바른 서명으로 로그인 200 / 동일 질문·응답 재전송 401. 다른 새 질문의 잘못된 서명도 401.
4. 같은 계정에 두 키 등록 → 하나 삭제 → 삭제 키 로그인 401 / 남은 키 로그인 200.
5. 로그아웃 뒤 이전 쿠키 재전송 401. 다른 계정 키 삭제 403. 마지막 키 삭제 409.

요청·응답 원문은 JSON `records`, 허용·거부 짝은 `pairs`, 시험 항목은 `checks`, 두 공개키 목록은 `keys`에 있다. 소프트웨어 인증기는 실제 갤럭시·지문 센서가 아니다. **운영 배포와 갤럭시 첫 키 등록·재로그인은 사용자가 완료했다. 기본 키 삭제 후 남은 키 인증까지 사용자 확인 완료했다. 실기기 A/B 자료 분리, 삭제된 키를 선택했다는 증거의 확정, 새 시크릿 창 공개 URL 확인은 남아 있다.**

## ⑥ 아직 못 막은 것

- **분실 복구:** 마지막 키 삭제는 막지만, 모든 저장소에 접근할 수 없으면 운영자의 본인 확인 복구 절차가 없다. 아이디만으로 복구해 주면 남의 자료를 넘길 수 있으므로 자동 복구는 제공하지 않는다.
- **공용 PC의 세션 노출:** HttpOnly와 한 시간 만료·최근 인증 제한이 있어도, 로그아웃하지 않은 PC를 다른 사람이 직접 사용하면 세션 유효기간 동안 본인처럼 행동할 수 있다. 패스키 추가·삭제도 최근 로그인 5분 안에는 세션만으로 가능하다. 중요 작업마다 별도 재인증을 요구하는 개선 여지가 있다.
- **인증기·제공자 신뢰:** attestation `none`을 사용하므로 특정 제조사·하드웨어 보안 수준을 보증하지 않는다. 저장소 선택란은 사용자 설명이다. 저장소 계정·기기 잠금이 탈취되면 앱만으로 방어하지 못한다.
- **서비스 남용:** IP 해시별 5분 120회 옵션 발급 제한과 흐름별 미완료 질문 수 제한은 있지만, 분산된 대량 가입·DB 사용량 소진을 막는 운영 수준의 방어는 아니다. 공유 NAT 환경에서는 정상 사용자가 제한을 함께 받을 수 있다.
- **공개 소개 범위:** T01의 공개 이름·소개 배경은 이어받았다. 실제 비공개 연락처·민감한 기록은 넣지 않는다. 기존 공개 정보까지 익명화해야 하는 제출 해석이면 별도 조정이 필요하다.

### 추가 등록 피드백 수정

초기 UI는 오류를 페이지 상단에만 표시했다. 최근 인증 5분 초과로 서버가 거부하면 아래쪽 버튼 근처에서 아무 반응이 없어 보일 수 있음을 UI 시험으로 재현했다. 오류가 나는 최근 인증 제한은 유지하고 추가 버튼 옆에 진행·오류 메시지를 표시했다. 등록이 기기 창을 기다리는지, 서버 요청이 거부됐는지 구분한다. 통신은 20초 후 시간 초과를 안내한다. 기기 창 전환 중 비공개 DOM을 비우는 처리는 유지하며, 돌아왔을 때 서버 세션을 다시 확인해 화면을 복원한다. 사용자 현상의 정확한 원인이 5분 초과였다고 단정하지 않는다.

### 로그인 키를 구분하는 표시와 직접 확인

`/api/auth/me`는 인증된 본인 세션에 저장된 `credential_id`와 해당 키 이름만 추가로 돌려준다. 클라이언트가 보내는 키 이름·헤더·URL 값은 이 판단에 쓰지 않는다. UI는 `이번 로그인에 사용한 패스키`를 표시하고 로그아웃 때 지운다. 키 추가만으로 세션의 인증 키를 최신 키로 바꾸지 않는다.

각 키의 `이 패스키로 로그인 확인`은 새 서버 질문을 받고 브라우저 `allowCredentials`를 선택한 키 ID 하나로 제한한다. 이 값은 사용자 선택을 돕는 프런트엔드 필터이며 보안 판단을 대체하지 않는다. 응답 ID도 선택한 키와 비교한 뒤 서버에 보내고, 서버는 언제나 실제 저장 공개키로 서명을 검증한다. 성공 시 세션을 새로 발급하고 실제 인증 키를 표시한다. 다른 키 응답을 선택한 키의 성공으로 오인하지 않는 시험과 세션 복원 시험을 추가했다. 격리 Worker 검증은 실제 인증 키 표시 2항목을 포함해 46개 통과했다.

### 계정 지정 로그인과 남아 있는 저장소 항목

로그인 화면에 선택 사항인 가상 아이디 입력란을 추가했다. 입력하면 서버가 현재 DB에 남아 있는 해당 사용자의 credential ID만 allowCredentials로 요청한다. 새 challenge의 user_id도 지정 계정에 묶고 검증 시 대조한다. 후보 제한을 제거한 B의 유효 서명도 A 지정 질문으로는 통과하지 못한다. 없는 아이디에는 같은 형태의 가상 후보를 반환하며 어떤 실제 키 서명으로도 그 질문을 통과할 수 없다. 등록 이름·공개키·메모·세션은 공개하지 않는다. 아이디를 비우면 기존 discoverable 인증을 유지한다.

이 방식은 삭제된 키가 휴대폰 저장소에 남았을 때 유효 키로 진입하도록 돕는다. 저장소의 실제 삭제·동기화 상태를 이 앱이 보장하지는 않는다. 계정 후보 ID의 개수·응답 차이로 등록 상태를 추측하는 공격을 완전히 막지는 못하며 IP 기반 옵션 발급 제한만 있다. 아이디를 안다는 것만으로 키 등록·기존 자료 접근을 허용하지 않는다.
