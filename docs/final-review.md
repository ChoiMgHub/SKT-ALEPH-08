# 과제 8 · 최종 검수 기록

검수일: 2026-10-27 (한국시간)

## 판정과 남은 제출 절차

공개 소개 확장, 패스키 등록·서명 인증·로그아웃·계정별 메모, 두 키 등록·삭제 후 남은 키 인증, 직접 접근·재전송 차단을 구현·검증했다. 사용자 갤럭시 실기기, 로컬 시험, 격리 workerd, 실제 운영 HTTP 결과를 구분해 기록했다. 가명 표시·최종 문서를 반영한 소스를 마지막으로 업데이트·배포하고 새 시크릿 창에서 공개 첫 화면을 확인한 뒤 제출한다. 최종 평가 결과를 미리 보장하는 문서는 아니다.

운영 HTTP 검사는 당시 배포된 기능 소스 `08483949c9da99ec23844381d40e783df16cdf42`를 대상으로 했다. 최종 변경은 공개 표시 이름 가명화·문서·검증 도구이며 인증·소유권 검사를 완화하지 않았다.

운영 허용·거부 기록:

- 본인 조회200 / 익명 조회401.
- A→B와 B→A 원문 조회·수정·삭제403, 피해자 건수·원문 전체 불변.
- 정상 서명 로그인200 / 잘못된 서명401 / 동일 질문·본문 재전송401.
- 로그아웃 전 조회200 / 옛 쿠키 재전송401.
- 같은 계정 두 키 등록 → 하나 삭제 → 삭제한 정확한 ID로 새 서명 로그인401 / 남은 키200.
- A 지정 질문에 B의 정상 서명도401, 남은 A 키로는200.
- 마지막 키 삭제409, 다른 계정 키 삭제403.

운영 검사 전용 임시 계정 2개는 모두 삭제했다. 사용자 learner_a·learner_b에는 접근하지 않았다. Cookie·Set-Cookie 값은 가리고 속성만 보존했다. 개인키는 실행 메모리에서만 사용하고 파일에 저장하지 않았다. 운영 검사도 소프트웨어 인증기이며 내 지문 센서 시험과 같다고 적지 않는다.

## 내가 갤럭시에서 확인한 과정

1. 학원 PC의 Windows 계정·PIN을 바꾸지 않고 갤럭시 Chrome에서 사이트를 열었다.
2. learner_a 첫 키 등록, 로그아웃 후 지문 승인 로그인, 메모 3개와 키 목록을 확인했다.
3. 추가 등록 무반응·중복 거부를 겪고 실제 메뉴 화면을 전달했다. 휴대폰의 기본 서비스 설정과 사이트의 기록용 선택란을 구분했다.
4. 같은 계정에 기본 키와 예비 키가 따로 등록된 목록·날짜를 확인했다.
5. 서버의 `이번 로그인에 사용한 패스키: 내 갤럭시 예비 키`로 예비 키 인증을 확인했다.
6. 사이트에서 기본 키를 삭제하고 예비 키 하나만 남은 뒤에도 예비 키로 인증했다.
7. learner_b 등록·로그인 후 A로 돌아오지 못한 문제는 수정본 배포 후 아이디 지정 A 로그인에 성공해 확인했다.
8. A/B에서 서로의 메모가 보이지 않는 것을 확인하고 두 계정의 JSON을 내려받았다.

과거 일반 로그인 실패가 삭제된 기본 키 때문인지는 그 요청 ID가 없어 확정하지 않는다. 삭제 키 거부는 운영 HTTP에서 별도로 증명했다.

## 실기기 JSON 검수

원본 두 파일은 사용자가 보관·선택 첨부한다. 이 저장소에는 자동 복제하지 않고 검수 결과와 원본 해시만 기록한다.

| 항목 | learner_a-evidence.json | learner_b-evidence.json |
|---|---|---|
| 크기 | 5,157 bytes | 2,989 bytes |
| 생성 한국시간 | 2026-10-27 15:03:13 | 2026-10-27 15:01:52 |
| 기록 | 로그인 옵션·검증·메모·키 조회 4건 | 메모·키 조회 2건 |
| 메모 | 본인 소유 3개 | 본인 소유 3개 |
| 남은 키 | 내 갤럭시 예비 키 1개 | B 계정 테스트 키 1개 |
| 로그인 원문 | 성공200, 공개키로 서명 별도 검증 성공 | 이번 파일에는 없음 |
| 비밀값 | 비밀번호·쿠키·토큰·개인키·API 키 없음 | 동일 |

사용자 ID는 다르고 메모 ID 중복은 0개다. 각 메모의 user_id가 해당 응답 사용자를 가리키며 다른 계정 본문이 섞이지 않는다. 두 파일 모두 기본 가상 메모 3개이며 별도 'A/B 계정 전용 메모' 제목을 추가 저장한 증거는 아니다.

A의 서버 질문·clientData challenge·origin·userHandle·credential ID와 남은 예비 키가 일치했다. 첨부 공개키를 사용한 독립 서명 검증도 성공했다. UV·UP 플래그가 있지만 지문을 썼다는 사실은 내 설명이고 JSON에 지문 원본이 담긴 것은 아니다.

SHA-256:

```text
learner_a-evidence.json
ae2769fc40bdadbff2043b3570336ae24a577e124b43f509974c492048cd60ff

learner_b-evidence.json
77ceec465cd33b0a3f2aef0e1d92b34bfda3498f5e119a62224336a6765c2259
```

실기기 파일에는 타인 원문 직접 요청403·삭제 키401·질문 재전송401이 없다. 그 항목에는 운영 HTTP 원문을 함께 사용한다. 공개키·credential ID·서명은 비밀번호·개인키가 아니지만 실제 개인 메모를 넣었다면 원문 공개 전 별도 검토해야 한다. 이번 첨부 내용은 가상 자료다.

## 공개 정보와 남은 위험

현재 T08 화면은 `학습자 A(가명)`과 `contact@example.invalid`를 사용하고 메모는 가상임을 표시한다. T01 소개 구성·학습 배경·활동·근거 링크는 이어받되 T01 원본 저장소와 이전 Git 이력을 삭제한 것은 아니다.

휴대폰 인증 창에는 삼성 패스가 표시됐다고 보고했다. 앱 저장소 필드 `Google 비밀번호 관리자`는 자기 기입 값이며 실제 제공자를 자동 판별했다고 취급하지 않는다. 서버는 이름·제공자 필드 대신 키 ID와 공개키 서명으로 인증한다.

전체 키 분실 시 복구 절차 부재, 공용 PC의 유효 세션 직접 사용, 제공자·기기 잠금 탈취, 대량 가입·자원 소진 방어 한계가 남아 있다. 마지막 키 삭제 차단은 모든 분실 상황을 복구해 주지 않는다.
