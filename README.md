# SKT-ALEPH-08 · 내 소개 페이지에 패스키 달기

과제 1의 공개 소개 `index.html`에 계정별 비공개 메모와 패스키 등록·로그인·관리를 추가한다. 비공개 메모는 서버의 로그인·소유권 검사를 통과한 뒤에만 내려온다. 사이트 비밀번호는 만들지 않는다.

**현재 단계: 앱 구현·운영 배포·실제 갤럭시 시험·최종 운영 HTTP 검사 완료. 제출용 문서와 가명 표시를 정리했다. 마지막 소스 업데이트·배포 후 새 시크릿 창에서 공개 첫 화면을 확인하고 제출한다.**

- 로컬 자동 테스트 26개 통과.
- 기존 격리 workerd/D1 검사 46개 통과.
- 실제 배포 Worker·원격 D1의 HTTP 검사 46개 통과. 이 검사 전용 임시 계정 2개를 생성·삭제했고 `learner_a`·`learner_b`는 접근하지 않았다.
- 사용자 갤럭시: 등록·지문 승인 재로그인·두 키 등록·기본 키 삭제 후 남은 키 인증·A/B 목록 분리·A 계정 복귀 로그인 완료.
- 제출 증거와 범위: [최종 검수](docs/final-review.md), [인증 설명 여섯 항목](docs/auth.md), [운영 요청·응답 원문](docs/production-evidence.json).

Node 24 이상과 npm을 사용한다. 학원 PC의 Windows 계정·암호·PIN을 바꾸지 않는다. 아래 블록은 실패하면 이후 명령을 실행하지 않는다.

```powershell
cd "$HOME\Documents\Aleph_Choi\SKT-ALEPH-08"
& {
  git pull --ff-only
  if ($LASTEXITCODE -ne 0) { throw "소스 업데이트 실패" }
  npm.cmd ci
  if ($LASTEXITCODE -ne 0) { throw "의존성 설치 실패" }
  npm.cmd test
  if ($LASTEXITCODE -ne 0) { throw "자동 테스트 실패" }
  npm.cmd run build
  if ($LASTEXITCODE -ne 0) { throw "빌드 실패" }
}
```

### 갤럭시에서 시험하기 위한 HTTPS 배포

```powershell
& {
  npm.cmd run db:remote
  if ($LASTEXITCODE -ne 0) { throw "DB 준비 실패: 배포를 중단합니다" }
  npm.cmd run deploy
  if ($LASTEXITCODE -ne 0) { throw "배포 실패" }
}
```

DB 명령의 진행 질문에는 대상이 **aleph-profile-08**인지 확인하고 `y`. `schema.sql`은 `CREATE ... IF NOT EXISTS`이며 기존 자료를 삭제하지 않는다. T06·T07 DB에는 실행하지 않는다. API 인증 오류가 나면 `npx.cmd wrangler logout`, `npx.cmd wrangler login` 후 실패한 DB 명령부터 재시도한다. 비밀 파일이나 AUTH_PEPPER 설정은 이 과제에 필요하지 않다. Worker 주소·RP ID는 `wrangler.jsonc`의 고정 주소를 사용한다. 다른 주소로 바꾸면 그 주소에서 패스키를 새로 등록해야 한다.

### 선택: PC 로컬 개발

```powershell
npm.cmd run setup:local
npm.cmd run db:local
npm.cmd run dev
```

`http://localhost:8787`로 접속한다. 이 주소는 해당 PC에서만 열린다. 갤럭시에서 `localhost`를 입력하면 갤럭시 자신을 뜻하므로, 실제 기기 시험은 **배포된 HTTPS 주소**를 사용한다. `.dev.vars`는 로컬 주소 설정이며 Git에 올리지 않는다. 로컬과 배포 주소에 등록한 패스키는 별개다.

## 실제 사용 순서

1. 배포 주소를 갤럭시 Chrome에서 열기. 공개 소개는 로그인 없이 보인다.
2. 아래의 '처음 사용하나요?'를 펼쳐 실명·이메일 대신 `learner_a` 같은 가상 아이디를 입력한다. 키 이름과 실제로 선택할 저장소를 기록하고 패스키를 등록한다.
3. 기기가 표시하는 등록 창에서 Google 비밀번호 관리자 등 지원 저장소를 확인한다. 앱의 저장소 선택란은 기록용이다. 사이트가 지문·PIN·패턴 원본을 받지 않는다.
4. 로그인 후 가상 메모 3개, 패스키 이름·등록 날짜·저장 공개키를 확인한다. 로그아웃하고 같은 키로 다시 로그인한다.
5. 두 번째 별도 패스키를 같은 계정에 추가한다. 기기가 다른 저장소를 지원하는지 확인한다. 같은 키가 동기화되어 다른 기기에도 보이는 것은 별도 키가 아니다. **사용자가 갤럭시의 기본 서비스를 Google로 바꾼 뒤 같은 계정에 별도 키 두 개를 등록한 화면을 제공했다.** 지원하지 않으면 다른 개인 기기·지원 저장소를 확보해야 한다. 가상 인증기를 실제 키로 가장하지 않는다.
6. 계정 B를 따로 만들어 자료 분리 시험을 한다. '같은 계정의 두 키'와 '서로 다른 두 계정'은 별도 시험이다.

키 추가·삭제는 마지막 로그인 후 5분 이내에 한다. 시간이 지나면 로그아웃 후 재로그인한다. 로그인에 사용한 키를 삭제하면 그 키로 만든 세션도 회수되어 즉시 로그아웃된다. 남은 키로 다시 로그인한다. 마지막 키 삭제는 차단한다. 모든 키와 제공자 복구 수단을 잃으면 이 앱은 기존 계정을 복구하지 못한다.

## 시험·증거

- `npm.cmd test`: 실제 검증 라이브러리와 SQLite를 통한 서버·UI 자동 시험. 지문 센서 시험은 아니다.
- `npm.cmd run build`: 브라우저 라이브러리와 Worker를 로컬 번들로 만들며 CDN 스크립트를 쓰지 않는다.
- `npm.cmd run evidence:build`: 빌드된 Worker를 격리 workerd/D1에서 실행하고 소프트웨어 인증기의 실제 P-256 서명으로 허용·거부 요청을 재검증한다. 먼저 build가 필요하다. 운영 DB와 사용자 계정은 접근하지 않는다.
- 공개 증거: `/verification.html`, `/verification.json`. 로그인·계정 생성 없이 열 수 있도록 배포한다. 격리 환경임을 상단과 JSON에 표시한다.
- 브라우저의 '현재 확인 기록 JSON 내려받기': 해당 브라우저 API 기록. 쿠키·세션 토큰·개인키는 수집하지 않는다. 계정 별칭·메모 원문은 포함될 수 있으므로 공개 전 점검한다. 로그아웃·탭 숨김·계정 변경 시 화면과 기록을 비운다.

## 추가 등록 버튼을 눌러도 반응이 없어 보일 때

초기 화면은 서버 오류를 페이지 위쪽에만 표시해 아래의 추가 버튼 근처에서 안내를 놓칠 수 있었다. 수정본은 버튼 바로 아래에 진행·오류를 표시한다. 로그인 후 5분이 지나면 서버가 추가 등록을 403으로 거부하므로, 기존 키를 삭제하지 말고 로그아웃 후 재로그인해서 시도한다. 20초 네트워크 시간 초과도 안내한다. 기기 인증 창 때문에 탭이 숨겨졌다 돌아온 경우, 실패 후에도 서버 세션을 다시 확인해 본인 화면을 복원한다. 사용자의 실제 원인이 5분 초과였다고 확정한 것은 아니며 수정 후 표시 문구로 구분한다. DB 구조·기존 키·메모는 변경하지 않는다.

## 이번 로그인에 사용한 키 확인

`learner_a`는 계정 이름이므로 삼성 패스·Google 양쪽에 같은 이름으로 보일 수 있다. 비공개 영역의 `이번 로그인에 사용한 패스키`는 서버 세션의 `credential_id`에 연결된 실제 인증 키 이름이다. 최신 등록 키를 임의로 표시하거나 사용자가 선택한 저장소 이름만 보고 추정하지 않는다. 키를 추가해도 기존 세션의 인증 키는 바뀌지 않는다.

예비 키 카드에서 `이 패스키로 로그인 확인`을 누르면 새 서버 질문을 받아 브라우저의 allowCredentials 후보를 그 키 ID 하나로 제한한다. 다른 키 응답으로 성공했다고 표시하지 않는다. 서버는 기존 공개키 서명 검증을 그대로 수행하고 새 세션을 발급한다. 성공 후 서버의 실제 인증 키 이름을 표시한다. 이 버튼은 자체적으로 새 로그인 인증을 하므로 먼저 로그아웃할 필요가 없다. 저장소 제공자의 화면이 어느 것처럼 보이는지만으로 성공을 판단하지 않는다. 개인키·세션 토큰을 표시하지 않으며 DB 구조 변경은 필요 없다.

## 삭제한 키가 기기 목록에 남아 A 계정으로 돌아가지 못할 때

사용자는 `learner_a`의 예비 키 인증과 기본 키 삭제 후 남은 키 인증을 서버 표시로 확인했다. 이후 `learner_b`를 만들어 로그인한 뒤, 일반 로그인에서 삼성 패스의 `learner_a`를 선택하자 검증 실패가 나타났다고 보고했다. 삭제된 기본 키가 저장소에 남아 선택됐을 가능성이 있지만, 사용자가 선택한 실제 credential ID를 확인하지 않았으므로 원인·삭제 키 거부 성공으로 확정하지 않는다.

로그인 버튼 위 `로그인할 가상 아이디 (선택)`에 `learner_a`를 입력하고 기존 패스키로 로그인한다. 서버가 현재 등록된 해당 계정의 키 ID만 인증 후보로 돌려준다. 아이디 입력은 계정 생성·키 복구·비밀번호 인증이 아니다. 실제 키의 서명을 확인해야 로그인된다. 아이디를 비우면 기존 기기 계정 선택 방식도 사용할 수 있다. 질문은 지정 계정에 묶이므로 클라이언트가 후보 필터를 바꿔 B의 정상 서명을 보내도 A 지정 요청으로는 거부한다. 없는 아이디에는 가상 후보를 돌려주고 검증은 거부한다. 계정·키·DB 구조를 다시 만들 필요 없다.

## 최종 운영 HTTP 확인

`npm.cmd run verify:remote`는 이 프로젝트의 실제 배포 주소에서 고유한 임시 계정 두 개를 만들고 검증 후 삭제한다. 개인키는 실행 메모리에만 있고 결과 파일에 내보내지 않는다. 원문은 `docs/production-evidence.json`, 사용자 실기기 파일의 검수 요약과 해시는 `docs/final-review.md`에 있다. 운영 검사도 소프트웨어 인증기이며 사용자 지문 동작을 대신했다고 적지 않는다. 이미 수행한 최종 검사 결과가 있으므로 제출을 위해 이 명령을 다시 실행할 필요는 없다.
